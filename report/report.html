LiveRecall: revision-aware caption delivery with bounded recovery

CS3103 Assignment 4 · Pranav Mahatma (A0281778L) · Final code: tag final-2 (server identical to candidate-2) · Official numbers: Ubuntu VM (UTM), median of 3 runs

1. Architecture and protocol

The server (solution_server.py) is a single Python 3.12 process running one asyncio event loop, using websockets 16.1.1. One source connection sends SOURCE_HELLO, then CAPTION_UPDATEs, then SOURCE_DONE. Many viewers connect with CLIENT_HELLO, which carries a resume cursor (last_segment, last_revision) and history_seconds. I kept the required message format unchanged.

caption_source ──► SessionState ──┬─► ClientSender 1 [bounded queue] ──► viewer 1 • final history │ (one sender task per client; (70 s, bounded)├─► ClientSender 2 ping every 2 msgs, ──► viewer 2 • active segments│ ≤2 unanswered) • highest seen └─► ClientSender N ◄── pong timing → slow-mode decision
  • SessionState holds the bounded final history, the latest revision of each active (not yet final) segment, and a high-water mark highest_segment_seen. The high-water mark means an evicted or retired segment can never come back.
  • ClientSender: each viewer has its own bounded queue and one sender task. That task sends recovery and live updates in order. The source only appends to queues and never waits for a client, so a slow client cannot block the source or other viewers.
  • Encode once: each update is serialised to JSON once, and the same string goes to every viewer. Large HISTORY replies are split into ordered frames under the client's 1 MiB message limit.
  • Validation: caption fields, session names (including UTF-8 validity) and the whole resume request are checked before the client is bound to a session, so a malformed message cannot corrupt state.
  • Browser client (client/): keeps one entry per segment and replaces it in place when a newer revision arrives (provisional in amber italic, final in black). It keeps finals locally for 70 s (at most 2000 segments, the same retention as the server) for the 15/30/60 s "What did I miss?" view (default 30 s). Its resume cursor is always the highest final it holds. It reconnects automatically with backoff from 0.5 to 5 s and asks for 60 s of history on every hello, so a late joiner gets a full view at once.

2. Revision and recovery semantics

  • Revisions: for an active segment, only a higher revision is accepted. Duplicates and older revisions are dropped. A final is immutable, so anything arriving for a segment after its final is ignored.
  • Recovery order: on (re)connect the server sends HISTORY with only the finals newer than the client's cursor, oldest first, then the latest state of every active segment, then live updates. A client is never sent a final it already reported.
  • No-gap handoff: the history/active snapshot and the registration of the client for live updates happen with no await in between. If an await sat between them, a final produced at that moment would be in neither the snapshot nor live delivery: a permanent gap. Registering first and taking the snapshot later would cause duplicates instead.
  • History window: following the course clarification, a client may request up to 60 s. Longer requests are capped to 60 s, not rejected; negative values are rejected. Internally I keep 70 s, a margin for timing jitter at the boundary. When a client overflows its queue (Section 3), the server resyncs it with only the finals it has not yet been sent, looking back over the full 70 s retained.

Evidence. In a matched reconnect check (55 segments), every reconnecting client got 55/55 finals, against 49/55 for the starter, which sends an empty HISTORY. In the official T4 runs, 120 to 140 items were recovered through HISTORY per run, with recovery P95 5.11 ms and 0 duplicate or stale messages.

3. Backpressure and overload policy

Fixed bounds, independent of lecture length and client speed:

  • History: 70 s, and also at most 32,768 items and 32 MiB.
  • Active (not yet final) segments: at most 128 items and 4 MiB. Over the limit, the server evicts the oldest open segment and keeps the source connected, so a source that never finalises some segments cannot block later finals. An evicted segment cannot come back (high-water mark). My first version closed the source connection here, which would have lost every later final; I changed it to eviction.
  • Per-client queue: soft limit 32 items or 256 KiB, hard limit 256 items or 2 MiB.

The policy has four layers:

  1. Coalescing. When a client is behind (its oldest queued item is older than 0.5 s, or it has more than 32 queued), I compact its queue: provisionals that a newer queued revision of the same segment replaces are dropped. Finals and the newest revision of each segment stay, in order. A client that catches up gets every revision again.
  2. Making the backlog visible. My first version never coalesced in T3. The reason was that the kernel TCP buffers and the client library's 16-message receive queue absorbed the backlog, so the server's queue looked empty while the reader fell many seconds behind. My fix is a ping send window: the server sends a WebSocket ping every 2 messages and waits once 2 pings are unanswered. The backlog then builds in the server's queue, where obsolete revisions can still be dropped.
  3. Slow mode (finals only). If a client's pongs show it has not read for at least 3 s, it is sent finals only for 15 s. The hold doubles each time it trips again, up to 120 s. Its newest provisional stays queued and is sent when the hold ends. A 500 ms reader can keep up with finals alone (about one per 0.75 s), so finals still arrive during the lecture rather than after it.
  4. Hard limit. If a queue still exceeds 256 items or 2 MiB, it is cleared and the client is resynchronised from shared history, starting after the last final it was sent. The client is not disconnected and loses no finals within the retention window.

This matches the course's guidance on graceful overload: finals are never dropped to make room for provisionals, the newest revision of each segment is kept, and no queue grows without bound.

3.1 The slow-mode trigger (four measured versions)

Getting the trigger right was the main engineering problem, because T3 (slow readers) and T5 (lossy link) pull it in opposite directions. In T5, WebSocket runs over TCP, so a lost packet blocks everything behind it until it is retransmitted (head-of-line blocking). The retransmission wait doubles each time (about 0.2, 0.4, 0.8 s), so several pongs from a healthy client can arrive late together. In T3, a trace of a 500 ms reader showed fast pongs for about 8 s while the buffers filled, then about 5.5 s of silence, then two late pongs at once.

A pong with latency L proves the client did not read for at least L seconds, so I time a streak from when the ping was sent. Time passing after the latest late pong proves nothing. Counting it let a 2.2 s pong plus a fast pong 0.9 s later add up to 3.1 s and trip slow mode. I rejected simply raising a single-pong threshold to about 2.5 s: one pong cannot tell "stopped reading" from an unlucky retransmission, and because retransmission waits double, a harsher link crosses any fixed value.

4.1 Interpretation

  • T1/T2 (scale): P50 rises from about 5 ms to about 12 ms going from 20 to 100 clients, because one event loop sends each update 100 times. P99 stays near 23 ms and everything is fresh.
  • T3 (slow clients): normal clients are isolated from slow ones: P95 is 18.84 ms and fresh, about the same as T2. The overall P95/P99 is dominated by the 10% slow readers, whose lag (about 6 s at P50) is the client library's 16-message buffer (16 × 0.5 s ≈ 8 s), which the server cannot see into. All 90 normal clients got every final in every run. The 0.39% missing is only the last 2 to 4 finals (from segments 73 to 76) of each of the 10 slow readers: they were sent, but were still waiting in the slow readers' buffers when the harness stopped recording about 3 s after the source's last final. With fewer segments (--source-segments 60), so the source ends earlier, T3 is 100%. Coverage below 100% is the slow readers' coalesced provisionals, the intended trade-off.
  • T4 (reconnect): disconnected clients resume from their cursor and are sent only the missed finals (120 to 140 items per run), within about 5 ms at P95, with no duplicates.
  • T5 (impairment): the 3% loss appears as delay, not missing data, because TCP retransmits. Finals stay at 100%. The ~120 ms netem delay applies in both directions on lo, a base round trip of about 240 ms, so P50 is near 263 ms. Retransmission with head-of-line blocking stretches the tail to about 700/1030 ms (P95/P99), and freshness falls to about 88% for the same reason. Under 2 Mbit, coalescing keeps P95 near 53 ms with full coverage.

4.2 Hypervisor timing and the capture cutoff

I first ran everything in a Multipass VM (Ubuntu 24.04.5, same CPU and memory). There, the prescribed T1 to T4 runs were all cut off: the harness wrote its results before the source sent SOURCE_DONE, so the last segments were never recorded, whatever the server did. I traced it to timer lag in the VM: each asyncio.sleep(0.2) in the source took 0.2517 s, and with three waits per segment a segment took about 0.905 s instead of the 0.75 s run_demo.py allows for. 6. Failures and trade-offs

  • Hidden backlog: my first coalescing design looked correct in unit tests but did nothing in T3, because buffers outside the server hid the lag. Finding out why coalescing never triggered exposed this, and it led to the ping window.
  • False slow-mode trips: the two-late-pong rule passed T3 but put 19% of healthy T5 clients in slow mode. My first fix (3a) broke T3, because it reset on fast pongs and timed from arrival. I found each problem by running both T3 and T5 after every change, not only the test I was fixing.
  • Remaining T5 trip: in one dev run a single healthy client returned a 4.0 s pong. It really did not read for 4 s, so under my definition it was unresponsive, and the cost was 15 s of finals only for that client. I accepted this; the official runs had 0 trips.
  • Rejected shortcut: during development I was offered the idea of sending live finals to slow clients labelled as HISTORY. The harness processes HISTORY without the simulated slow-reader delay, so it would have improved the metric by exploiting the measurement and misusing what HISTORY means in the protocol. I rejected it (AI_USAGE.md).
  • Resync versus disconnect: at the hard limit I resync from history instead of closing the socket. This costs one burst of finals but keeps the client's view complete, without a reconnect cycle.

7. Limitations

  1. Timing depends on the VM. The harness assumes the source keeps 0.75 s per segment. Under Multipass it did not, and the prescribed runs were cut off (Section 4.2). My official numbers come from the UTM VM, where timing is accurate; I did not modify the harness.
  2. Slow-reader lag floor of about 6 s at P50 for a 500 ms reader, set by the client library's receive buffer, which the server cannot observe or drop from. At the end of T3 it shows as the last two finals still unread when capture stops.
  3. Detection delay: a slow reader is caught only after about 6 to 8 s, once the buffers outside the server fill.
  4. Recovery window: recovery is guaranteed only for absences up to 60 s (70 s retained). An open segment evicted at the active-segment bound loses its later final.
  5. Scale: a single process on a single core, with one session per instance and no persistence. All results come from VMs on one laptop with uncontrolled host activity.

8. Future work / FYP direction

  • Measure reading speed directly with application-level acknowledgements, instead of inferring it from ping timing, and adapt the slow-mode threshold to each client's own round-trip time.
  • Use QUIC or WebTransport so that one lost packet does not block unrelated captions (no cross-stream head-of-line blocking), which addresses the T5 tail.
  • Fan out across processes or machines (pub/sub), with multiple sessions and persistent lecture history for revision after class.
  • Use live ASR as the caption source, plus per-student bookmarks and search over the recalled window: a natural FYP extension.
