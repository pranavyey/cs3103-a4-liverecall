**Generated design modified on 3 November 2026.** The first generated connection handler bound the server to a client's requested session before checking the rest of that client's request (last_segment, last_revision and history_seconds). So a malformed first client hello naming some other session (e.g. session BAD) with a negative last_segment was rejected, but the server was already bound to session BAD. Valid L1 clients could then no longer join. I reviewed the handler and rejected that ordering. The server now validates the whole request before it binds to any session. A regression test sends such a malformed hello first and then checks that normal L1 delivery still works.

**Additional correction recorded at the same gate.** During the same review, I found that an unpaired Unicode surrogate in a source session name could make logging fail after the source lease was acquired. The name is now checked for UTF-8 encoding before creating session state. A regression test verifies a later valid source can still connect.

**Generated design shown insufficient by measurement, 3 November 2026: slow-mode trigger.**

*Problem.* The first generated slow-client policy marked a client slow after one pong later than 1 s; the client then received only finals for at least 15 s. On a lossy link, one TCP retransmission can make a normal client's pong late, so a follow-up AI suggestion required two consecutive late pongs (bb50641). I accepted that on reasoning alone, without measuring it. Once SLOW_MODE_ENTER and CLIENT_STATS logging were added (e6fceec), one T5 run on the Ubuntu VM (delay_loss.sh: 120 ms ±30 ms, 3% loss, 100 normal clients, 40 s, no slow readers) showed 19 of 100 normal clients still entering slow mode, with pongs of 1.0 to 1.4 s and one at 2.2 s. Finals stayed at 99.98% with 0 duplicate or stale, but normal update coverage fell to 95.50%. Under this profile, a lossy link produces late pongs back to back, so two in a row was not enough.

*Attempts.* The new idea: a pong with latency L shows the client stopped reading at least L seconds earlier, when the ping was sent, so the rule asks whether late pongs prove at least 3 s without reading.

1. **2c0f320:** timed the streak from pong arrival. This broke T3: slow readers were never detected (local completeness 97.96%).
2. **d3142fa:** timed the streak from when the ping was sent. VM T5 false trips fell from 19 to 1, finals were 100%, and coverage was 99.66%.
3. **405da57 (final):** measures the streak only up to the latest late pong, as explained in the review-question entry below. VM, one run each: in T3 all 10 slow readers entered slow mode on their first late pong (late_for 6.0 s), and normal clients stayed 100% fresh with P95 20 ms. In T5, one client entered slow mode after a single 4.0 s pong, a real 4 s without reading. Under the 2 Mbit profile, a run short enough to avoid the capture cutoff reached 100% completeness and coverage. In the official runs (candidate-1, 3 runs each), T5 had 0 slow-mode entries.

*Why I chose this rule.* I used this rule over simply raising the late-pong threshold (for example to 2.5 s) for these reasons:

- A fixed cutoff on a single pong can't tell a client that stopped reading from one that hit an unlucky TCP retransmission.
- Retransmission timeouts double (0.2, 0.4, 0.8, 1.6 s), so a harsher lossy link would eventually cross any fixed value.
- The question that matters is how long the client went without reading, and that is what the late pongs measure.

I initially thought a slower trigger would lose important messages, but the data didn't show that: final completeness stayed at 99.98 to 100% in every T5 run. Finals are never dropped. Only provisionals that a newer revision has replaced are coalesced, and a queue overflow resynchronises the client from history rather than discarding finals.

**Generated explanation found incorrect, 3 November 2026: slow-reader pong pattern.** Claude Code explained why a slow reader defeated 2c0f320 as "a late pong immediately followed by a fast one", and put that wording into the d3142fa code comment and this document. Claude Code had inferred this from a debug log that printed only pongs over 0.3 s, and presented it as fact without verifying it against a full pong trace. I asked the AI how often the server pings each client, because the explanation did not fit my understanding of the ping design. As I remembered it, the server pings every 2 messages, which is about every 0.5 s or faster here. The 0.3 s figure in the explanation matched neither. It turned out to be the debug log's print filter, not a ping interval. More importantly, if one pong came back 2.2 s late, a ping sent 0.5 s after it should be stuck behind the same blocked data, so its pong should be late too, not on time. A full pong trace was then taken. It showed a different pattern: fast pongs for about 8 s while the TCP buffer and the client library's 16-message queue absorb the backlog, then about 5.5 s of silence once the library stops reading the socket, then two late pongs at the same instant, then a burst of fast pongs. The code comment and explanation were corrected to match the trace in 405da57.

**Flaw found through a review question, 3 November 2026: fast pongs extending a late streak.** In d3142fa, the slow-mode check compared the current time with the streak start, and it ran on every pong, including fast ones. Claude Code asked me whether a normal client with one 2.2 s pong followed by fast pongs would enter slow mode. Working through my answer showed it could: a fast pong 0.9 s later counted as 2.2 + 0.9 = 3.1 s of lateness, even though fast pongs show the client was reading. This is the likely cause of the one false trip in VM T5 run 3, whose SLOW_MODE_ENTER line showed a 463 ms pong. The check now measures only up to the latest late pong (405da57). Only late pongs count as evidence of not reading.

**Generated shortcut rejected, 3 November 2026: finals sent as HISTORY.** Codex proposed, during the Gate 3 work, sending live finals to slow clients labelled as HISTORY messages, which the public load client handles without its simulated slow-reader delay. I stopped it as disingenuous: it would improve the number by exploiting how the harness measures, not by making delivery to slow clients better, and it would misuse the protocol's meaning of HISTORY (recovery after a reconnect). The slow-reader lag floor is instead accepted and explained in DESIGN_NOTES.md Gate 4.
