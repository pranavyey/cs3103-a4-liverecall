This avoids the case where a caption arrives after the history snapshot but before the client joins live delivery. The implementation also shares serialized immutable caption strings across clients. **Generated design modified on 3 November 2026.** The first generated connection handler called session(...) before handle_client(...) validated last_segment, last_revision, and history_seconds. A malformed first client hello with session BAD and a negative last_segment was rejected, but had already bound the only session to BAD. Subsequent valid L1 connections could no longer join. Review rejected that ordering. The handler now calls client_resume(...) to validate the complete resume request before session(...) can change state. A regression test first sends the malformed request and then verifies normal L1 delivery succeeds. This is an actual correction made during this project, not a hypothetical example.

**Additional correction recorded at the same gate.** Review found that an unpaired Unicode surrogate in a source session name could make logging fail after the source lease was acquired. The name is now checked for UTF-8 encoding before creating session state. A regression test verifies a later valid source can still connect.

**Generated design shown insufficient by measurement, 3 November 2026: slow-mode trigger.** The first generated slow-client policy marked a client slow after one pong later than 1 s, and it then received only finals for at least 15 s. On a lossy link, one TCP retransmission can make a normal client's pong late, so a follow-up AI suggestion required two consecutive late pongs (bb50641). This was argued, not measured. With SLOW_MODE_ENTER and CLIENT_STATS server logging added (e6fceec), one T5 run on the Ubuntu VM (delay_loss.sh: 120 ms ±30 ms, 3% loss, 100 normal clients, 40 s, no slow readers) showed 19 of 100 normal clients still entering slow mode. Their pongs were 1.0 to 1.4 s, with one at 2.2 s. Finals stayed at 99.98% and duplicates/stale stayed at 0, but normal update coverage fell to 95.50% (97.71% in the first run). The two-late-pong rule was not enough: under this profile, a lossy link produces late pongs back to back. The trigger was changed again: a client is slow only if it has been unresponsive for 3 s, timed from when the late ping was sent (latency L means it stopped reading at least L seconds ago). The first attempt (2c0f320) timed the streak from pong arrival and broke T3, because slow readers answer rarely (about 5 s late, often two pongs at once); a logged run found this. The fix (d3142fa) was re-measured: T5 on the VM had 1 of 100 normal clients enter slow mode (was 19), 100% finals, 0 duplicates/stale, and 99.66% update coverage. Local T3 completeness was 98.98% (98.78% before), and all slow readers were still detected. [Student: add why you accepted this rule, in your own words.]
