One paragraph per gate: the problem, the design chosen and why, the evidence, and the remaining trade-off. Where I explained a gate's code path, state, bounds or failure case, the explanation is recorded under "My explanation" and reflects an actual conversation.

A dedicated Ubuntu VM provides the required Python and tc/netem environment. Baseline slow-reader runs expose substantial lag, while reconnect runs return zero recovered history items. **Gate 2 — server correctness candidate — 3 November 2026.** The server validates caption fields, accepts only increasing revisions for active segments, and treats final captions as immutable. It stores finite recent final history and the latest active state; a retained high-water mark prevents expired segments from reappearing. Reconnect selects recent finals newer than the client's finalized cursor, then a single sender emits history, active state, and live updates in order. Taking the snapshot and registering the client without an await prevents a gap between recovery and live traffic. Commit 36ed410 passed all fourteen integration tests, five bounded-state tests, and startup compatibility on Ubuntu. In the matched 55-segment reconnect check, every client now received all 55 finals; the baseline reconnecting clients received 49/55. No duplicate or stale state appeared. Prescribed runs retain a source/capture cutoff caveat; these one-run checks are not the final repeated experiment set. Evidence is in experiments/server-core/. This phase used a bounded FIFO with reconnect-on-overflow; Gate 4 replaced it with coalescing and resync. My explanation: I correctly explained final-revision immutability and that recent history is retained independently of whether existing clients received it, after clarifying that all missed finalized segments are recovered. I then explained the no-await handoff: an await between snapshot and registration would let a final miss both the snapshot and live delivery, a permanent gap. After a prompt, I also noted that registering first and snapshotting later would cause duplicates instead.

**Gate 3: browser client, 3 November 2026.** The client keeps one entry per segment. A newer revision replaces the old text in place, and a final segment never changes afterwards, so late, repeated or recovered updates are ignored. Provisional text is amber italic with its revision number; finals are black with a "final" tag. Finals are kept locally for 90 seconds (capped at 2000 segments; reduced to 70 seconds in candidate-2 to match the server), so the 15/30/60 second recall uses local state only, with 30 seconds as the default. The resume cursor is the highest final held, never a provisional one. On close, the client reconnects automatically with backoff from 0.5 to 5 seconds and shows its state. Every hello asks for 60 seconds of history, so a late joiner can use the 60 second view straight away. A "Simulate disconnect" button drops the connection for 8 seconds for the demo. tests/browser_e2e.js ran two tabs plus a late joiner in headless Chromium against a 60 second source. All three ended with finals 1 to 48, no gaps and no duplicate rows. The dropped tab recovered 12 finals from HISTORY and the late joiner 32. My explanation: I explained that recall uses the client's own store and that requesting 60 seconds avoids extra server requests. After correction, I noted that the main reason is giving a late joiner a full 60 second view. I explained the three duplicate/stale checks in apply(), with a correction that tooOld compares against the resume cursor. On the finalized cursor, I first suggested a provisional cursor would cause duplicates; the corrected reasoning is that it can make a server skip a segment whose final the client never received.

**Gate 4: slow-client isolation, 3 November 2026.**

*Design.* Each client has one sender task and a bounded queue, so a client that keeps up gets every revision. Once a client falls behind (oldest item waiting over 0.5 s, or more than 32 items queued), its queue is compacted: provisionals replaced by a newer queued revision of the same segment are dropped, while finals and the newest revision of each segment stay in order. If the hard bound (256 items or 2 MiB) is still exceeded, the client is resynchronised from shared history at the last final it was sent, instead of being disconnected.

*Finding: the hidden backlog.* TCP buffers and the client library's 16-message queue hid slow readers, so the server never saw a backlog. The server now pings every 2 messages and keeps at most 2 pings unanswered, which keeps the backlog in the server queue, where obsolete revisions can still be dropped. A client detected as slow gets finals only for 15 s, doubling on repeats up to 120 s, so its buffered backlog drains. One T3 run in the dev container, versus the previous commit: completeness 95.1% to 99.7%, slow-reader P99 24.0 s to 8.1 s, normal clients P95 under 14 ms and 100% fresh both times.

*Slow-mode trigger.* The first rule (one pong later than 1 s) and the second (two consecutive late pongs, bb50641) both put normal clients into slow mode on a lossy link: in VM T5, 19 of 100 normal clients tripped the two-pong rule, because head-of-line blocking behind a retransmitted segment delays several pings together. The final rule (405da57): a pong with latency L shows the client went at least L seconds without reading, measured from when the ping was sent. A client is slow only if its late pongs (over 1 s) prove at least 3 s without reading, measured up to the latest late pong. A streak ends after 1 s with no late pong; fast pongs neither start nor end it. The intermediate attempts are in AI_USAGE.md.

*Evidence.* VM, one run each on 405da57: in T3 all 10 slow readers were caught on their first late pong (late_for 6.0 s); in T5 delay/loss, one trip from a genuine 4.0 s pong; at 2 Mbit, 100% completeness once the run was not cut off. Official runs (candidate-1, median of 3, see Gate 6): T5 had 0 slow-mode entries, and supplemental T3 reached 100% completeness with normal P95 19.6 ms.

*Trade-off.* Slow readers receive fewer provisional revisions and stay about 6 s behind at P50 in 60 s runs. That lag sits in the client library's 16-message buffer, which the server cannot see. Detection only happens once that buffer fills, after about 8 s.

*My explanation.* I explained that only provisionals are dropped and finals are always kept. After correction, I noted the trigger is per client (queue age, item count, bytes) rather than total traffic. With an analogy, I explained that at most 2 unanswered pings keep the backlog in the server queue, where obsolete revisions can be dropped, and that slow mode switches the client to finals only for at least 15 s. Correction recorded: the hidden backlog sat in TCP buffers and the client library's queue. For the final trigger, I explained that for about the first 8 s a slow reader's pongs are fast, because the TCP buffer and the library's queue have not filled, so the library keeps reading the socket and answers pings immediately; only once the queue is full does it stop reading, leaving pings unanswered. I explained that two late pongs in a row is a poor test on a lossy link because data behind a lost segment waits for its retransmission; after correction, I noted that the sender keeps sending and the receiver delivers in order. I first explained the slow reader's pong pattern with the lossy-link mechanism, and was corrected with the trace. Asked whether a single 2.2 s pong followed by fast pongs trips slow mode, I reasoned correctly that 2.2 s is under 3 s, but initially said a fast pong ends the streak; working through this exposed the flaw fixed in 405da57. After correction, I noted that a slower trigger does not lose finals: only superseded provisionals are coalesced.

**Course clarification: bounded history, 3 November 2026.** Per the course's clarification, clients may request up to 60 s of history, and a request for more is served up to 60 s instead of being rejected; negative values are still rejected. Finals are retained for 70 s internally, a margin for timing jitter at the boundary, and server-initiated resyncs use the full 70 s. Item and byte caps (32,768 items, 32 MiB) are unchanged, so history stays bounded (79c9720, two new tests, 21 OK). VM T4 with --source-segments 40: 100%, 120 recovered items, 0 duplicate or stale. My explanation: I explained that the extra 10 s is a buffer so a final isn't missed at the 60 s boundary because of jitter or processing delay. I explained that history stays bounded so it can't grow without limit, and that since clients can request at most 60 s, keeping much more would not be useful; after correction, I noted the main risk of unbounded history is memory growing with lecture length, and that the bound is 70 s, 32,768 items or 32 MiB, whichever is hit first. I explained that capping a longer request serves as much history as the server allows, a better fallback than rejecting it; rejecting would close the connection and give the client no history at all.

**Active-segment overflow and client retention, candidate-2, 4 November 2026.** The server caps active (not yet final) segments at 128 items and 4 MiB. The generated server core closed the source connection when that cap was hit, which would have lost every later final. Over the cap, the server now evicts the oldest open segment and keeps the source connected; a revision too large to fit even alone is dropped and the previous one kept. An evicted segment cannot come back, so its later final is rejected. The server logs ACTIVE_EVICTED segments=N when the source disconnects. Three bounded-state tests cover eviction, 50 abandoned segments that still do not block later finals, and the byte cap; 22 tests pass. The deterministic source never has more than about 2 segments open, so this path cannot trigger in T1 to T5. The browser's local retention changed from 90 s to 70 s, the same as the server. My reasoning: I questioned whether 128 open segments was too many, since a hidden test might leave segments open instead of finalising them. After clarifying with Claude, I understood that the cap never limits finals, because it applies only to provisionals that open a new segment, but that closing the source was the real risk, so I chose eviction. I also asked whether server-initiated resyncs sending up to 70 s broke the spec. After clarifying with Claude, I understood that a resync sends only the finals the client has not yet been sent, with 70 s as the look-back limit; the 60 s limit applies to what a client requests in CLIENT_HELLO, which is capped, and the spec allows retaining more than 60 s within a fixed bound. I matched the client's retention to 70 s because a client can only request the latest 60 s anyway, so it doesn't change what the recall view shows.

**Review correction — validate before changing session state.** The first generated handler bound the single session before validating the reconnect cursor. A malformed hello could be rejected while still preventing later valid connections. I rejected that ordering in review; validation now precedes binding, and a regression test checks the failure case. During my review, I also found that an invalid Unicode session name could fail during logging and leave the source connection occupied; session names are now validated before state changes.
